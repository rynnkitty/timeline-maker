# Refactoring Guide Skill

## 목적
안전하고 체계적인 리팩토링을 위한 기법과 절차를 제공합니다.

## 리팩토링 기법 카탈로그

### 메서드 수준

#### Extract Method
```
상황: 하나의 메서드가 너무 길거나 여러 책임을 가짐
방법: 논리적 단위를 별도 메서드로 분리
주의: 추출 후 원본 메서드의 가독성이 향상되는지 확인
```

#### Inline Method
```
상황: 메서드 본문이 이름만큼 명확
방법: 메서드 호출을 본문으로 대체
주의: 하나의 호출처에서만 사용될 때 적합
```

#### Replace Conditional with Polymorphism
```
상황: switch/if-else 체인으로 타입별 분기
방법: 각 분기를 서브클래스/전략 패턴으로 전환
주의: 분기가 3개 이상이고 확장 가능성이 있을 때
```

#### Introduce Parameter Object
```
상황: 동일 파라미터 그룹이 여러 메서드에 반복
방법: 파라미터를 하나의 객체/클래스로 묶음
주의: 관련 파라미터끼리 묶되, 무관한 것은 포함하지 않음
```

### 클래스 수준

#### Extract Class
```
상황: 하나의 클래스가 너무 많은 책임
방법: 관련 필드와 메서드를 새 클래스로 분리
주의: 기존 public 인터페이스 유지 (위임 패턴)
```

#### Move Method/Field
```
상황: 메서드/필드가 다른 클래스에 더 적합
방법: 해당 클래스로 이동, 원본에 위임 메서드 잔류 가능
주의: 이동 후 의존 방향이 개선되는지 확인
```

### 데이터 수준

#### Replace Magic Number with Constant
```
상황: 코드 내 의미 불명의 리터럴 값
방법: 이름 있는 상수로 추출
예시: 86400 → SECONDS_PER_DAY
```

#### Encapsulate Field
```
상황: public 필드에 직접 접근
방법: private 필드 + getter/setter (property)
주의: 기존 접근 코드를 모두 변경해야 함
```

## 리팩토링 절차

```
1. 현재 동작 확인 (테스트 존재 여부 확인)
   ↓
2. 리팩토링 범위 결정 (한 번에 하나만)
   ↓
3. 변경 실행 (작은 단위로 나누어 진행)
   ↓
4. 동작 확인 (기존과 동일한 결과)
   ↓
5. 다음 리팩토링 또는 완료
```

## 리팩토링 하지 말아야 할 때
- 납기가 임박한 경우
- 테스트가 전혀 없고 추가할 시간도 없는 경우
- 곧 폐기될 코드
- 완전히 이해하지 못한 코드 (먼저 이해부터)
- 기능 변경과 동시 수행 (분리 필수)

```markdown
### After

(동일 동작 확인 방법)
```
